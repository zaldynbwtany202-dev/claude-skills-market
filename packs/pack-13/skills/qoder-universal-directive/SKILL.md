# الأمر الشامل لـQoder — التعليمات الدائمة

النص الكامل كما أراده المستخدم محفوظ في `reference/directive-source.md`. هذا الملف هو الاختصار Operational الذي يُنفَّذ. الوجهة دائمًا **Qoder نفسه**: لا OpenCode ولا أي تطبيق آخر؛ ملفات OpenCode مصدر للفحص والنقل فقط.

## ١. ترتيب العمل في كل مهمة غير بسيطة

1. افهم النتيجة المطلوبة والمخرجات ومعايير القبول والقيود والمخاطر قبل اختيار أي أداة.
2. اقرأ كتلة `[THEMAGICSCAN]` المحقونة تلقائيًا. إن لم تظهر:
   `node C:\Users\Admin\.qoder\themagicscan\router.mjs "<الطلب>"`
3. حدّد طبيعة المهمة: بحث / تحليل / إنشاء / برمجة / تصميم / تشغيل / استكشاف عطل / مقارنة / تخطيط. لا سير عمل واحد لكل شيء.
4. اختر كل قدرة تضيف قيمة أو تغطي جزءًا أو تقلل مخاطرة. لا تستدعِ قدرة بلا غرض، ولا تقلّص الفريق لتوفير الاستدعاءات.
5. نفّذ، ثم ادمج المخرجات، ثم تحقّق بدليل، ثم سجّل feedback وذاكرة.

## ٢. حالات القدرة (استخدم هذه بالضبط، ولا تخلط بينها)

`مكتشفة` → `مقروءة` → `مثبتة/مسجّلة` → `مهيّأة` → `متاحة في الجلسة` → `قابلة للاستدعاء` → `استُدعيت` → `أنتجت نتيجة` → `تحقّق`
وسوم النهاية: `completed` / `failed` / `skipped_with_reason` / `unverified`.

وجود اسم في فهرس أو في ملف **ليس** دليلًا أنها متاحة أو تعمل. عدد الأدوات الحي يُقرأ من التطبيق نفسه، لا من نص الإعداد.

## ٤. المرحلة التأسيسية (جرد واستيراد)

- قارن عنصرًا عنصر بين المصدر وQoder: موجود ومتاح / موجود جزئيًا / غير مسجل / غير قابل للنقل / مكرر / غير متاح.
- ثبّت أو سجّل أو حوّل ما هو متوافق ومطلوب. لا تنسخ صيغة غير متوافقة كما هي.
- لا إسقاط بصمت: لكل عنصر غير منقول اذكر الاسم والسبب الدقيق (ملف مفقود / صيغة غير متوافقة / اعتماد خارجي غير مثبّت / مفتاح API أو اشتراك مطلوب / محظور / مكرر / غير آمن) وبديلًا داخل Qoder إن وُجد.
- لا خدمة مدفوعة ولا حساب ولا مفتاح API بلا تفويض صريح. لا تطلب OAuth رفضه المستخدم من قبل؛ اذكر العائق مرة واحدة والبديل.
- لا تحذف ولا تستبدل إعدادًا قائمًا بلا مبرر؛ خذ نسخة احتياطية قبل أي تغيير مؤثر.
- المكتبة ليست محذوفة ولا مهملة: كل المهارات مفهرسة في المخزون، والنداء التدريجي هو الحل — الفهرس يعطي المسار، والعقد يسمّي القدرتين أو الثلاث التي تخدم الطلب، فتُقرأ تعليمات تلك فقط. لا يُحقن المخزون كله ولا تُدمج 1,667 مهارة في الجذر المحمّل لأن ذلك يدفع سياقًا في كل رسالة.
- تجديد تلقائي: `staleness.mjs` يمرّ على الطبقة الأولى من جذور القدرات (skills، skills-library، agents/plugins، .qoder/plugins/cache، ملفات الإعداد) ويقارن بأحدث `index.generatedAt`. عند اكتشاف أجدّ يwarn في العقد ويطلق `build-index.mjs` في الخلفية (قفل 15 دقيقة، مخزن مسح 5 دقائق). مقيس على هذا الجهاز: مجلد مهارة جديد لا يرفع mtime أبوه في NTFS، لذلك يُعدَّ كل مدخل على حدة (~100ms).
- لا تعتبر المرحلة منتهية قبل تقرير استيراد لكل عنصر: المصدر، الحالة قبل، الإجراء داخل Qoder، الحالة بعد، دليل الاختبار، أو سبب عدم الإتاحة.

## ٥. الاختبار والإثبات

- معيار قبول قابل للملاحظة قبل إعلان النجاح.
- افصل ثلاثة مستويات: فحص الإعداد/الملفات، اختبارات الوحدات، والتشغيل الحقيقي داخل جلسة Qoder. نجاح وحدة ليس دليل تشغيل.
- في العمل المركب أو عالي المخاطر: افصل المنفّذ عن المراجع، وأعطِ المحكّم الأدلة والمعيار دون توجيهه لحكم إيجابي.
- لا تخلط نتيجة محاكاة أو fixture تنفيذي (مثل `THEMAGICSCAN_FORCE_ERROR`) بالتشغيل الحقيقي.
- لا تُخفِ عيبًا أو اختبارًا فاشلًا لتحسين الأرقام؛ لا تحذف سجلات append-only لإخفاء تكرار أو فشل.

مواصفة طويلة متعددة الأقسام فيها أسئلة تظل **طلب عمل** (`execute` أو `mixed`)، وتُستخرج أجزاؤها. قواعد القرار:

- `orchestrator.mjs:253` المواصفة الطويلة = طول + خطوات/مخرجات، لا الطول وحده.
- `orchestrator.mjs:264` أمر تنفيذي داخل اقتباس أو بعد نفي صريح ليس طلب عمل.

- `router.mjs:375` الفجوة تُعلن بسبب قابل للتشخيص بدل `required=0` صامت.

الحماية باختبارات الانحدار: `node routing-eval.mjs` (36 حالة عربية/إنجليزية) و`node --test themagicscan.test.mjs` (39 اختبارًا) و`node scenario-tests.mjs` (27).

## ٧. الذاكرة: engraphis وملفات المشروع

engraphis خادم ذاكرة محلي على `http://127.0.0.1:8711/mcp` (تسع أدوات، حالته تُقرأ من `index.json` الذي يبنيها `build-index.mjs` من Qoder الحي). مستشارٌ قبل المهمة، لا مصدر حقيقة المشروع ولا بديلًا عن ملفات المشروع أو فهرس القدرات.

- **قبل التنفيذ**: `engraphis_recall_context` بموضوع المهمة وميزانية رموز مناسبة (600 مقيسة تُرجع حزمة مضغوطة بتوفير ~85%). لا تعتمد على أعلى نتيجة وحدها: افحص لكل نتيجة `relative_score` و`absolute_support` و`workspace` و`source`.
- **الصلة بالمشروع**: حيّز `default` عام، و`video-editor`/`video-generator` لمشاريع الفيديو. معرفة مشروع مثل scene-forge قد تكون في ذاكرة الملفات فقط؛ إذا كانت الصلة ضعيفة أو الحيّز آخر فارجع لملفات المشروع وسجلاته وقل ما وجدته هناك.
- **القِدم والتعارض**: عند احتمال معلومة منتهية استخدم `engraphis_conflict_review`، أو افحص `supersedes` و`provenance` بـ `engraphis_get_memory` أو بسعة `why` عبر `engraphis_execute_read`. لا تخلط حيّزًا بآخر.
- **الكتابة اختيار لا عادة**: `engraphis_session` و`engraphis_remember` فقط لقرار مستقر موثّق يفيد لاحقًا — مع مصدره وسياقه وتاريخه. لا أسرار ولا مفاتيح، ولا نسخ المحادثة أو الملفات، ولا تسجيل التخمين كحقيقة. الحفظ حالة مشتركة: لا تبادر به بلا طلب ما دام المستخدم لم يقرّر سياسة الحفظ.
- **المسار المحكوم**: `engraphis_discover_actions` أولًا (يعيد `capability_id` و`schema_digest`)، ثم `engraphis_execute_read` أو `engraphis_execute_action` بهما. لا تخترع فعلًا ولا بصمة، ولا تكرر اكتشافًا صالحًا في نفس الجلسة.
- **ذاكرة الملفات تبقى الأسبق** لتفضيلات المستخدم وقواعد المشروع (`C:\Users\Admin\.qoder\memory\MEMORY.md` وذاكرة المشروع)، وengraphis طبقة ثانية عبر الجلسات. الخطاف يذكّر بذلك: سطر «ذاكرة engraphis» آخر العقد، يُزاح تحت سقف 1200 حرفًا ولا يزيح اختيار القدرة.

## ٨. الأسلوب والتقرير

- ابدأ بالخلاصة، ثم خطوات واضحة، ثم الحالة وما بقي والخطوة التالية (تفضيل المستخدم: عرض بسيط بالعربية، بلا جداول كبيرة أو مصطلحات إنجليزية).
- للتقرير: ما فُحص ومصدر كل رقم وتاريخه، كيف قُسّمت المهمة وما اختير لكل جزء ولماذا، ما استُدعي فعلًا ومخرجاته، ما راجعه المحكّم ومعياره، نتائج الاختبارات على ثلاثة مستويات، ما لم يعمل أو لم يُتحقق منه وسببه، الحكم (نعم/جزئيًا/لا)، ثم أهم خطوة تالية وحدها.
